# D3: CUDA evaluation

Dependency choices: optional `gremlin-cuda` crate with a `cuda` Cargo feature, NVCC-compiled CUDA C++ kernel, and CUDA static runtime. No CUDA headers, libraries, tools, or driver are needed for feature-disabled CPU builds. NVCC is discovered from CUDA_HOME (default /usr/local/cuda); actual compiler, runtime, driver, and device identities are recorded. This uses the installed CUDA toolkit rather than adding a Rust CUDA abstraction dependency.

Execution: 128-thread blocks tile the input set for each program; each thread evaluates one input. Register-major storage places adjacent cases of each register contiguously, including edge scratch registers. Narrow division uses 32-bit arithmetic for widths up to 32, with a separate 64-bit path; shift counts use a mask because all supported integer widths are powers of two. Each program is compiled from validated canonical CFG IR into a typed transport; it retains instruction/terminator budgets, simultaneous edge binding, traps, modulo shifts, and width-masked signed patterns. Register and edge-scratch memory are bounded by a caller memory budget and allocated in batches. Calls are explicitly unsupported by this backend; they remain a CPU module feature. No program is silently rerouted to different semantics.

A CLI worker with an external wall watchdog wraps native GPU calls. Kernel loops additionally obey the semantic step budget. Infrastructure, driver, compilation, and memory failures are run errors. CPU and GPU search must consume identical RNG streams and rank exactly the same fitness; timing is telemetry only.

Validation host supplied by user: NVIDIA RTX A4000 (16 GB), driver 590.48.01, CUDA toolkit 13.0.88. Rust 1.90.0 was installed in the remote account for testing. Transfer only source/manifests/tests, never local tokens or run credentials. Required GPU CI must fail explicitly if the feature/device is absent. Gate: >=10,000 seeded programs, all integer widths/operators, divergent CFGs, traps/timeouts, and corpus sizes 1/31/32/33/65. Measure marshalling/setup/transfers/kernel and end-to-end synthesis; do not infer acceleration from kernel time.

Implemented interface: build `cargo build --release -p gremlin-cli --features cuda`, then opt in with `[search.cuda]`, `memory_budget_mb = 1024`, and `wall_timeout_ms = 30000`. CPU is the default. Each population batch runs in a separate CUDA worker; the parent enforces a wall deadline and kills a stalled worker. The worker validates normalized IR, signature, input encodings and total device allocation before launch. Oversized batches fail with their required bytes; they are not silently truncated. Calls remain explicitly unsupported. Search generation/selection RNG order and stable fitness ordering are unchanged. Resume recalculates stored fitness on CPU. `cuda-batches.jsonl` records per-batch device, driver/runtime/compiler identity, allocation bytes, setup, transfer, kernel, host and worker wall times; the final integrity manifest covers it.

Initial measurements with JSON worker responses on the supplied RTX A4000 (compute capability 8.6), CUDA runtime 13.0 / driver 13.1, NVCC 13.0.88:

- 10,000 seeded programs, all eight integer types, valid operators, divergent CFGs and loops, case counts 1/31/32/33/65, and budgets 0/1/64: **4,860,000 exact outcome/step comparisons passed**.
- Across 120 batches: setup 99.53 ms, transfer/allocation 159.25 ms, kernel 13.35 ms, total host evaluator 947.54 ms. CPU evaluation plus comparison took 980.28 ms. Aggregate evaluator throughput was 5.13 million candidate-cases/second on CUDA and 4.96 million on the CPU comparison path; the latter includes assertion overhead and is not a controlled speedup comparison.
- Full composed-u64 synthesis with seed 1: CPU 0.948 seconds, CUDA 4.263 seconds, both generation 10 / 639,416 candidate-case executions, identical complete search states and E2 candidate. Fresh worker/context initialization and transport make CUDA slower for this workload. No end-to-end acceleration claim.
- CUDA synthesis resume, 1 ms watchdog, 1 MiB memory rejection, and hidden-device error tests passed. Infrastructure failures record no evidence level.

Raw parity timings and compact synthesis measurements are checked in under `docs/measurements/`. Commands: `cargo test --release -p gremlin-cuda --features cuda` and `cargo test --release -p gremlin-cli --features cuda --test cuda`. The manual CUDA workflow requires a self-hosted `gremlin-cuda` runner; registering that CI runner is a deployment task. Without one the workflow is unexecuted, not a passing GPU gate. The measurements above were run directly over SSH on the supplied GPU machine.


## Binary worker responses

Detailed worker evaluation returns a versioned little-endian binary response (`GRCUDA01`), including errors and telemetry. Each execution uses 18 bytes: outcome tag (1), integer type tag (1), value bits (8), and exact step count (8). Timeout and the two supported arithmetic traps have distinct tags. Numeric timings, driver/runtime versions and allocated bytes use fixed-width fields; device/compiler strings are length-prefixed and capped at 64 KiB. The complete response remains capped at 256 MiB. Decoding rejects unknown versions/tags/types, malformed dimensions, truncation, trailing bytes, noncanonical value bits and unsupported outcome payloads. The parent also checks dimensions, return types and step counts against its request. Requests remain JSON; human-readable telemetry files remain JSONL.

A controlled evaluation-only benchmark used the same seeded requests on a Ryzen 7 5700 (single CPU interpreter thread) and RTX A4000. Times below are medians of three runs; each GPU worker is a fresh process. Timing includes request serialization and response transport/decoding, but excludes search evolution/fitness/checkpoint work, telemetry log append and the parent's watchdog polling. The old and new measurements ran sequentially, not concurrently.

| Programs × inputs | Instructions per program | CPU | JSON worker | Binary worker |
| --- | ---: | ---: | ---: | ---: |
| 256 × 448 | 8 | 12.5 ms | 277.8 ms | 160.9 ms |
| 256 × 448 | 100 | 171.9 ms | 325.2 ms | 198.0 ms |
| 1,024 × 1,024 | 100 | 1,563.6 ms | 1,379.5 ms | 382.0 ms |
| 2,048 × 1,024 | 100 | 3,143.9 ms | 2,688.7 ms | 562.7 ms |

At the largest size, response size fell from 186,651,116 to 37,749,050 bytes, with a 4.78× worker speedup and 5.59× speedup versus CPU. All 10,125,312 evaluations per backend matched exact outcomes and steps. These straight-line add/XOR/multiply/rotate workloads do not establish a general search speedup; short candidates still favor CPU. The unchanged kernel's warm in-process performance remains faster than the fresh worker path. Raw timings, request hashes, compiler/device telemetry and measurement scope are in [cuda-binary-response.json](../measurements/cuda-binary-response.json).


## Compact fitness responses for search

Search sends the expected corpus values and comparator configuration with the evaluation request. After CUDA evaluation, the worker aggregates results with the same Rust scoring implementation used by CPU search. The default comparator, bit-error-first comparator and bounded custom Gremlin comparator preserve their existing exact-match precedence and tie-breaking. Custom costs retain the full unsigned 128-bit sum. Comparators are parsed once per batch.

The response uses tag 2 under `GRCUDA01`, with 80 bytes per candidate: noncompleted count, mismatch count, summed bit errors, total steps, trap/timeout/invalid counts, and an optional 128-bit selection cost (presence tag plus two words). The parent retains instruction count and canonical program bytes for tie-breaking. It validates summary dimensions, counts, score representation and bounds. Detailed tag-1 responses remain available to diagnostic callers. JSONL telemetry includes `response_kind` and `response_bytes`.

Both CPU and GPU populations keep compact fitness, preserving complete search-state parity. Population checkpoint `cases` arrays are empty. Resume recomputes fitness on CPU; it can also verify detailed fitness records when present. Final reports replay the best candidate on CPU, check its totals against the stored summary and retain detailed per-case diagnostics. The existing executable identity check still requires the same build for resume.

Aggregation currently runs on the worker's CPU after CUDA returns its execution matrix. It removes the large worker-to-parent transfer, but does not yet reduce device-to-worker results or avoid fresh CUDA context startup. Moving reduction into a CUDA kernel would be a separate optimization.

A fresh three-repeat benchmark includes evaluation **and scoring** on all paths (so times are not directly comparable to the evaluation-only table above):

| Programs × inputs | Instructions | CPU scoring | Detailed GPU response + parent scoring | GPU worker scoring + summary |
| --- | ---: | ---: | ---: | ---: |
| 256 × 448 | 8 | 13.5 ms | 240.4 ms | 226.7 ms |
| 256 × 448 | 100 | 197.0 ms | 277.7 ms | 284.5 ms |
| 1,024 × 1,024 | 100 | 1,657.6 ms | 511.2 ms | 493.3 ms |
| 2,048 × 1,024 | 100 | 3,317.0 ms | 766.5 ms | 639.0 ms |

The largest response shrank from 37,749,050 to 164,150 bytes (230×). Its evaluation/scoring latency improved by about 17%, with a 5.19× speedup versus the CPU interpreter plus scoring. The small 100-instruction batch was slightly slower; no universal speedup is claimed. All 10,125,312 candidate-case evaluations yielded matching complete summary fields. Separate hardware integration tests confirm default/custom-comparator search-state parity, resume, watchdogs and resource errors. [Raw results](../measurements/cuda-summary-response.json) include request hashes and all repetitions.

## Bounded flight-controller workload

[Landing Lab](../../apps/landing-lab/README.md) exercises long, branching programs with physics loops using the general CUDA interpreter. Three same-host comparisons of 128 controllers × 8,192 flights measured median search times of 78.71 s CPU and 1.098 s GPU (71.7×); including setup and holdout validation gives 49.8×. The baseline is the single-thread Gremlin interpreter, not compiled native physics. All candidate outcomes and instruction counts match. The app retains a context across eight batches; this is not a fresh CLI worker per batch. Full timing scope and raw results are in the app documentation and measurements.

The revised register layout, 128-thread tiling, narrow division and shift-count masking passed the 10,000-program CUDA parity gate, plus partial-tile/loop-edge tests at 127/128/129/255/257 inputs. Historical measurements above describe the versions at which they were taken.
